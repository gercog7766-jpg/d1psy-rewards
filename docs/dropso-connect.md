# Dropso Connect 1.0.1

Owner-only CS2 desktop integration at `/admin/connect`. The sidebar links to the page and an authenticated download. The checked-in gzip contains a standalone Windows x64 executable (no Node, Go or .NET installation required). The download endpoint streams the decompressed executable with its Windows file name. `public/downloads/DropsoConnect.json` records the uncompressed SHA-256 and size.

The Go application runs a native Windows notification-area icon and a local browser settings panel, starts disconnected every time, and supports a user-selected HKCU Run entry. Its Windows process survives closing the settings tab. Exit/disconnect are available through the tray. It detects Steam libraries (including additional drives) or accepts the CS2 install root, and writes only `game/csgo/cfg/gamestate_integration_dropso.cfg`. A remembered custom install path is the only saved configuration. The owner pastes a 24-hour, scoped random key from the admin panel before streaming; it is never saved to disk. Rotate/revoke ends existing sessions immediately. No administration or Supabase credentials ship with the app.

CS2 sends GSI on loopback port 28743, guarded by a per-run random secret. The local settings page and actions require their own per-run key and a same-origin request. No external listeners, DLL injection or game-memory access are used. The first installation requires restarting CS2. Closing/reopening the application refreshes the GSI secret; if CS2 was already running, restart it to reload the configuration.

Telemetry is limited to the provider's own Steam player, app 730. The server receives a sanitized snapshot and computes changes inside one locked database transaction. The first snapshot, a changed map/player, warmup/menu, and a score reset establish a baseline. A win requires an observed transition in the same round from a non-over state to over, won by the player's unchanged team. Round numbers are zero-based as reported by GSI. A sequence retry cannot pay again; out-of-order/expired snapshots cannot replay awards. Reconfiguration resets both rule periods and baseline. A new manual connection starts fresh counters and limits. A failed award rolls back the snapshot, allowing a safe retry.

Rules: every N kills, every N won rounds, separate on/off and coins/skin ranges; game-mode allowlist; per-rule cooldown; activity lookback; minimum unique viewers; valid Trade URL; exclusion of the immediately previous winner; session award count and budget. Kills use player.state.round_kills, never match totals. Kill progress resets each round and triggers at most once per round; a cooldown can defer it only within that same round. SteamID is pinned by the first session snapshot. Both enabled rules may trigger on the same snapshot; each picks one eligible viewer. Budgets count coins and catalog skin value and stop further rewards without debiting a personal/partner wallet. Only the site owner can configure or connect, because these are site-issued rewards.

Verified Twitch EventSub messages are recorded before normal giveaway channel routing. Each registered non-banned, unrestricted viewer has one entry per connection; their latest verified message determines eligibility for the current rule period. Participation starts at connection time and after the previous trigger of that rule, and is capped by the configured lookback. Empty/ineligible chat consumes the event without money movement and records a skipped result. Expired/no-longer-connected sessions cannot collect a fresh audience. Viewer selection uses the existing cryptographic index function, with equal probability per person. Coin awards use the existing ledger; skins use the existing Dropso inventory/claim/sell flow. Writes of reward, history, limits and sequence are atomic.

## Build and validation

With Go 1.25.4 available, `scripts/connect/build.sh` runs desktop unit tests, cross-compiles the Windows GUI executable, and regenerates the reproducible gzip plus manifest. Commit the gzip and manifest, not the uncompressed intermediate `.exe`. The Windows GitHub Actions job also tests native code and smoke-starts the actual Windows application, checks that the process stays alive, and denies unauthenticated panel/GSI requests. Server/PGlite/UI tests run in the normal deploy gate. Actual CS2 and the owner's interactive desktop must still be checked on the owner's PC; a synthetic smoke check cannot prove live-game integration.

Apply `dropso_connect` migration before deploying the server. It only adds private service-role tables/functions and starts disabled. No existing giveaway settings or wallet balances change. Database APIs are security invoker with a fixed empty search path, RLS on all new tables, and no anon/authenticated grants. Keep historical sessions and awards for audit; later retention work can remove old chat rows without deleting awards.
