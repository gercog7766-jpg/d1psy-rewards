# Закрытый стримерский пилот на основном сайте

Этот выпуск объединяет вход/заявки/админку и тестовый движок на `https://d1psy-rewards.onrender.com`. Настоящие награды и коммерческое включение других стримеров остаются заблокированы. Это не миграция тестовых денег в настоящие и не включение старого MULTISTREAM_DB_ENABLED.

## Контрольная точка и откат

До выпуска: main `9591e64afe7fe977503340dd2e665ebcc3a10629`, последний live build `e4d2ec3e53ee55daaa84359e211435c0f670ab35`, deploy `dep-dbneefk9v7es73ci78a0`. Между этими версиями только тест; исполняемый код одинаковый.

Read-only baseline базы 07.11.2026 12:20:29 Europe/Berlin: 321 legacy rounds, active=0, 2563 wins, 2297 coin entries, pilot tables=0. Это контрольные счётчики, **не полная резервная копия**. Пользовательская активность может менять счётчики независимо от выпуска.

Миграция добавляет только `rewards_pilot_*` таблицы/функции. Не меняет существующие функции, таблицы наград, личные деньги, призовой остаток и Twitch-подписки. Default: выключено, test_only=true с CHECK, профилей/одобрений/денег нет. Новые функции имеют SECURITY INVOKER, пустой search_path и service_role-only EXECUTE. RLS включена, anon/authenticated запрещены.

Первый уровень отключения: `/admin/streamers` → «Отключить и вернуть резервы». Выключатель в одной транзакции ждёт текущие операции, запрещает новые, отменяет тестовые раунды и промокоды, возвращает только неиспользованные тестовые резервы. Старый основной движок и его настройки не затрагиваются.

Второй уровень: развернуть сохранённый commit `9591e64afe7fe977503340dd2e665ebcc3a10629` или прежний live build. Перед откатом отключить пилот; если интерфейс недоступен, владелец может вызвать service-only `rewards_pilot_api('511100980','switch','{"enabled":false}')`. Новые таблицы оставить: старый код их не использует. Не удалять журнал и не откатывать реальные пользовательские данные. Удаление таблиц не требуется для отката приложения.

## Что доступно

- `/streamer`: подписанная обычная сессия сайта; форма имени/своего Twitch-login/ссылки; закрытый allowlist d1psy_off и amych. Numeric ID берётся только из серверной сессии, login сверяется с зарегистрированным Twitch-пользователем. До одобрения управление закрыто.
- `/admin/streamers`: существующая admin-сессия плюс SQL-проверка именно владельца primary канала. Заявки, одобрение/отказ/приостановка, отдельный тестовый бюджет и журнал, выключатель. Старое enabled amych не является одобрением.
- Одобренному каналу: время 1–3600 сек., сообщения 5–1000, диапазон цены 2–1000; резерв при старте, один участник на раунд, повторная проверка eligibility при выборе; отмена/пустой раунд возвращает стоимость один раз. Каждый запрос блокирует только профиль нужного канала; общей блокировкой пользуется лишь аварийный выключатель.
- Подключение Twitch создаёт подписку текущего main-приложения для ID вошедшего пользователя без изменения общего connection status. Старт требует подтверждённой enabled-подписки с нужными broadcaster/user IDs и main callback. OAuth-согласие из другого приложения на isolated API не переносится автоматически.
- Отдельный OBS: кнопка генерирует 256-битную ссылку только для чтения. Токен в URL fragment, запросы с Authorization; база хранит SHA256, query/path не содержат секрет. Смена ссылки отзывает старую. Выборка строго по профилю токена, без бюджета/чужих наград. При выключении/приостановке доступ закрывается.
- Промокоды только тестовые, на предметы: `TEST-...`, до 1000 активаций, срок до 30 суток, полная стоимость зарезервирована заранее. Активация/лимит/тестовая награда транзакционны. Неиспользованный остаток возвращается при отмене/истечении. Старый обработчик реальных промокодов не переиспользуется.
- Проверка промокода и тестовые награды зрителя внизу `/streamer`. Основной инвентарь не меняется; тестовые предметы нельзя продать/получить доставкой.

## Маршрутизация

Проверенная подписанная main EventSub notification вызывает новый атомарный pilot chat RPC до HTTP-ack. Для d1psy_off это теневая тестовая запись; прежний primary-путь продолжает работать. amych и неизвестные каналы не попадают в общий legacy engine. При отключённом пилоте pilot RPC не пишет сообщения/раунды. Изолированный API продолжает существовать отдельно и не пересылает тестовые события в production.

На первом этапе chat events должны приходить именно в main Twitch-приложение: авторизоваться на основном сайте, подключить канал из дашборда. Настоящий тест двух чатов требует действий владельцев аккаунтов; сессии/согласия за них не создаются.

## Проверки

Новые SQL/PGlite, HTTP и DOM тесты проверяют: заявки/owner-only управление, два канала с одинаковым message_id, независимые бюджеты/раунды/истории, подмену чужого round ID, повторы старта/пополнения, пустой time-раунд, граничные лимиты, промокод/повтор/возврат, свой OBS и отзыв, приостановку, общий выключатель, нулевые записи в настоящих wins/coins/rounds и неизменность призов. HTTP тест запускает настоящий server-entry, подписывает webhook и подтверждает сохранение legacy primary-пути, блокировку неизвестного канала, session/Origin/JSON checks. DOM покрывает pending-доступ, безопасный вывод имён и nonce после потерянного ответа.

PGlite сериализует обращения: Promise.all проверяет повторяемость, но не заменяет реальную двухсоединительную PostgreSQL-проверку блокировок. Живой пилот остаётся выключенным по умолчанию до ручного одобрения/пополнения и действий двух владельцев.

## Сценарий приёмки

1. d1psy_off и amych входят на **основной** сайт и подают свои заявки на `/streamer`.
2. Владелец на `/admin/streamers` одобряет оба профиля, выдаёт каждому тестовый бюджет и включает закрытый тест.
3. Каждый открывает свой дашборд, подключает свой Twitch, получает свою OBS-ссылку. Если grant отсутствует — повторный Twitch-вход на основном сайте; через несколько секунд повторить start после включения подписки.
4. Одновременно запустить 5 сообщений у одного и 30 секунд у другого, писать в оба чата. Проверить свои счётчики/победителей/OBS и изменение только своего тестового бюджета.
5. Проверить остановку одного канала при продолжающемся другом, тестовый промокод и повтор его активации, смену OBS-ссылки.
6. Отключить пилот из админки и проверить возврат незавершённых резервов. Настоящие предметы/монеты не должны появляться от теста.
7. Только после приёмки отдельно внедрять единую реальную выдачу в `rewards_wins` с атрибуцией стримера. В этом выпуске такого пути нет.

## Проверка после применения миграции

В основной PostgreSQL дополнительно выполнен service_role-сценарий внутри BEGIN/ROLLBACK: временные заявки двух каналов, одобрение, тестовые пополнения, два активных раунда одновременно, stop amych с сохранением primary-раунда, общий выключатель. Все условия прошли, транзакция целиком отменена: профилей, одобрений, ledger, раундов и наград не осталось. Это проверка реальных определений/прав и совместимости каталога, но не двух параллельных соединений и не живых чатов.

Полный набор после изменений: 50 тестов прошли, 0 пропущено; TypeScript build прошёл. Подтверждено, что control.enabled=false, test_only=true, реальные wins/coin entries не изменились при миграции и проверке.

## Готовая панель amych и проверка OBS

Панель показывает подтверждённую готовность main Twitch-подписки отдельным read-only endpoint, счётчик и таймер, число зарегистрированных зрителей с действующей Trade URL и без ограничений, резерв раунда и доступный тестовый бюджет. Опрос состояния продолжается во время ввода без сброса формы. После завершения доступен ручной следующий запуск; автоповтор не добавлен. Стоп виден постоянно и блокируется при отсутствии активного раунда.

Промокоды показывают активации, локальный срок и неиспользованный резерв; копирование и отмена доступны только для своего списка. Admin-кнопка одобрения теперь показывает «Одобрен» и не приглашает повторять действие.

OBS: готовая страница с каналом, прогрессом/таймером и победителем на 12 секунд. После этого возвращается текущий раунд либо ожидание. URL fragment сохраняется при перезагрузке, но не передаётся в HTTP URL; токен идёт только в Authorization и не даёт управляющих прав. Неверная/отозванная ссылка прекращает опрос, отключённый тест и временный сетевой сбой показываются отдельно. В кабинете есть копирование ссылки, предпросмотр и подтверждённая ротация. Существующие токены не меняются при публикации.

Дополнительные HTTP/DOM сценарии проверяют подтверждённое подключение, обновление при фокусе в форме, последующий ручной запуск, nonce промокода при потерянном ответе, копирование/предпросмотр, fragment после reload, победителя, отключение и отзыв. SQL-тест проверяет два разных канала/токена и отсутствие пересечений. Живой Browser Source в приложении OBS требует открыть персональную ссылку самим владельцем; на момент проверки у amych ссылка ещё не создавалась. Реальная выдача не включается этим выпуском.

## Тестовое предложение Dropso для новых стримеров

На публичной странице `/streamer` размещено предложение тестового подключения: 200 стримерских монет после одобрения заявки, начисляемых администрацией для первых розыгрышей. Число розыгрышей зависит от выбранных призов. Указаны независимость от личного кошелька, отсутствие переводов между балансами и пополнение только администрацией. Показаны кабинет, OBS, профиль с отметкой «Стример» и каталог каналов. Тест без обязательств; полноценное партнёрство обсуждается отдельно.

Это информационное предложение, без автоматического пополнения или изменения экономики. Гости переходят к существующему входу Twitch в блоке заявки, pending-заявки видят предложение и текущий статус. Для approved предложение скрывается и остаётся рабочий кабинет. На административной странице блока нет. Состояния, переходы и отсутствие POST при просмотре проверяются в `tests/streamer-production-ui.test.mjs`.

## Назначение без заявки

Админка → Стримеры → «Назначить стримера»: поиск зарегистрированного пользователя по имени/логину с пагинацией, назначение или восстановление доступа. Используется тот же approved-профиль, что после заявки. Стример открывает кабинет по существующей ссылке «Стримерам» и сам подключает Twitch. Статус сразу учитывают каталог стримеров, плашки и порядок пользователей. Бюджет пополняется прежней отдельной операцией администратора, без стартового автозачисления.

Новые service-role-only RPC rewards_streamer_live_assign / rewards_streamer_live_candidates проверяют владельца по неизменяемому Twitch ID основного канала. HTTP связывает actor с сессией, защищён adminAuth, Origin/JSON и throttle. Цель назначения — UUID существующего незаблокированного пользователя; логин и URL формируются из его Twitch-профиля. Повтор уже одобренного назначения не меняет OBS, контакт, баланс или журнал. Изменение статуса записывается в существующий audit. Назначение не включает глобальный режим дропов и не обходит Twitch OAuth/подключение.
