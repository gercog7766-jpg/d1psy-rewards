# Проверка объединения стримерских дашбордов — 07.11.2026

Статус: объединение технически возможно, но текущие ветки **не готовы к прямому включению multistream на основном сайте**. Этот документ фиксирует аудит и проект интеграции; он не является сообщением о выполненном запуске.

Проверены основной код `9591e64afe7fe977503340dd2e665ebcc3a10629`, изолированный API `1632266d4ffa9174589532e54fa4c369b14d80ab`, определения таблиц/индексов и функций основной Supabase. Данные читались без изменений. Тестовые бюджеты, победители и предметы не переносились в production. Twitch-согласия за владельцев не выполнялись.

## Подтверждённые препятствия

1. В основном `src/engine.ts` глобальный флаг `checking`, а чтение активного раунда не ограничено каналом. В `src/server-next.ts` аналогичные общие чтения и stop всех active-раундов. Два активных канала приведут к неоднозначному maybeSingle или остановке чужого раунда.
2. Основная база содержит обе формы исторических раундов: 123 со streamer_id=NULL и 198 с заполненным streamer_id (в момент проверки всего 321, активных 0). Имеются разные уникальные индексы для NULL и каждого streamer_id. Нельзя просто предположить, что первичный канал всегда NULL или всегда backfilled. Нужен единый primary scope и явно проверенная миграция.
3. `src/multistream-engine.ts` основной ветки выбирает и вставляет приз отдельными запросами; `tickStreamerRounds` не подключён к startup. В основной базе нет RPC `rewards_streamer_start_round`, `rewards_streamer_stop_round` и атомарного chat ingestion, которые ожидает подготовленная тестовая ветка.
4. В основной `src/eventsub.ts` 204 отправляется до завершения обработки; dedup, chat log и счётчик пишутся отдельно. Ошибка после dedup может потерять сообщение при повторе. Ошибки/отзыв доступа не должны менять статус другого канала. Неизвестный broadcaster должен отклоняться, а не попадать в первичный канал.
5. OBS activity выбирает последнюю запись `rewards_wins` по всему сайту, включая магазин/апгрейдер/чужие каналы. Даже при правильных отдельных раундах виджет останется общим без отдельного фильтра источника.
6. `src/promo-code-hotfix.ts` записывает награду до уникальной записи активации, а счётчик меняет отдельно. По исходному коду возможны лишняя награда и неверный лимит при конкурирующих запросах. Эксплуатационные запросы к production не выполнялись. Такой обработчик нельзя повторно использовать как готовый механизм стримерских промокодов.
7. В production `amych` уже есть в старом `rewards_streamers` с enabled=true, но drops_enabled=false, Twitch disconnected. Эта техническая запись не является заявкой или одобрением новой системы. Не переносить enabled в approved автоматически. Первичный d1psy_off подключён; его работа должна сохраняться.
8. Сейчас все 62 available-приза имеют unlimited=true. Поэтому конфликт конечного остатка не проявляется на текущих данных, но поддержка конечных предметов всё равно должна быть атомарной. Не превращать магазинные-only товары в пул дропов.

## Целевая модель

Один сайт, одна учётная запись зрителя и один `rewards_wins`/инвентарь. Отдельно для каждого стримера: одобрение, подтверждённая Twitch-идентичность, состояние подписки, настройки, раунды, участники, бюджет, промокоды, журнал и OBS-токен.

### Заявки и доступ

- `/streamer` доступен авторизованному пользователю. Без approved показывает только форму «Имя», «Ник Twitch», «Ссылка на Twitch», «Подать заявку» и статус рассмотрения.
- Ник и ссылка должны соответствовать Twitch-ID вошедшего пользователя; одних полей формы недостаточно для владения каналом. ID берётся из проверенного OAuth, не из JSON запроса.
- `/admin/streamers`: список заявок, одобрить/отклонить, приостановить, бюджет и история пополнений. Обработчик проверяет владельца сайта на сервере; стример не получает административную роль.
- После одобрения стример отдельно подтверждает Twitch-разрешения для чтения своего чата. Проверяются token validation и Helix identity; сохраняется состояние разрешения/подписки для конкретного канала.
- Приостановка блокирует новые действия и промокоды, безопасно отменяет незавершённые обязательства и возвращает резерв ровно один раз. Старые выигрыши зрителей не удаляются.

### Бюджет и промокоды

- Стримерский бюджет не является `rewards_coin_transactions` и не входит в личный баланс пользователя. Только владелец сайта создаёт пополнение. Никакого вывода, самостоятельного пополнения или перевода в личные монеты.
- Старт блокирует кошелёк нужного стримера, проверяет approval/разрешения/лимиты, выбирает разрешённый приз и резервирует стоимость в одной транзакции. Отмена/нет подходящих участников возвращают резерв; победа окончательно расходует его. Стабильный request ID защищает повтор после потери ответа.
- Для промокода фиксируются награда, владелец, срок, лимит и резерв всей максимальной выдачи. Неиспользованный резерв возвращается при отмене/истечении один раз. Активация блокирует код, проверяет лимит и одно использование зрителем, создаёт награду и меняет счётчик одной транзакцией.
- Типы награды промокода нужно явно определить при реализации. Предметы идут в инвентарь; если предусмотрены монеты зрителю, это отдельная награда из зарезервированного промобюджета, а не доступ стримера к обычному кошельку. Прямой обмен своего dashboard-баланса в личный баланс запрещён.

### Розыгрыш, события, OBS

- В базе — не более одного active-раунда на streamer_id; блокировки на кошельке/настройках/раунде согласованы. При работе с конечным остатком резервирование исключает двойное обещание одного предмета.
- Событие Twitch сначала проверяется по подписи, подписке и broadcaster_id. Дедупликация, привязка к активному раунду, участие, счётчик и окончание — транзакционно. Успешный HTTP-ответ после сохранения; сбой допускает безопасный повтор.
- Не добавлять в уже начавшийся раунд запоздавшие события, относящиеся к предыдущему. Участник имеет одну запись на раунд; право на выигрыш проверяется повторно при выборе (бан/ограничения/условия участия).
- Серверный таймер обходит каждый канал отдельно, переживает перезапуски, не зависит от открытой страницы или OBS. Завершение и повтор события не создают вторую награду.
- OBS имеет собственную ссылку на канал и токен только для чтения; чужую личную информацию, budget API и управление он не открывает. Показывает только свой раунд и свои выигрыши, с атрибуцией имени канала. Старую ссылку можно отозвать сменой токена.
- В основном инвентаре выигрыш содержит источник «Стример: amych» либо другой канал. Источник не меняет владельца предмета и не даёт стримеру доступа к Trade URL зрителя или админской доставке.

## Проверки до включения

1. Два одобренных тестовых стримера одновременно запускают time/message-раунды; одинаковые Twitch message IDs разных каналов не пересекаются.
2. Старт/стоп/настройки/промокод/OBS одного канала не изменяют другой; подмена streamer_id в URL/body бесполезна.
3. Pending/rejected/suspended и неизвестный broadcaster не могут запустить, создать код, получить чужой OBS-токен или бюджет.
4. Два старта на последний бюджет, финализация vs стоп, два одинаковых webhook, потеря HTTP-ответа, два последних redeem — без перерасхода и повторной награды.
5. Реальный PostgreSQL проверяет блокировки и откаты. PGlite и source-regex-тесты не заменяют проверку двух соединений.
6. Конечный и unlimited приз, отсутствие доступных призов, отключение товара, shop-only товары, отсутствие подходящих зрителей.
7. Инвентарь/продажа/выбор/доставка/push работают с наградами обоих стримеров; один зритель может выиграть у обоих без второго аккаунта.
8. Одобрение, отказ, повторная заявка, отзыв, смена Twitch-login при неизменном numeric ID, истечение согласия и перезапуск сервиса.
9. Primary канал сохраняет актуальный раунд и историю, старый NULL-scope не создаёт второй primary-раунд. Rollback не выдаёт награды повторно и не теряет бюджет.
10. Сверка остатков: пополнения минус окончательные расходы минус активные резервы равны доступному бюджету; личный кошелёк стримера не изменился.

## Фактически выполненные проверки

Изолированный API: `npm test` — 73 теста, 70 прошли, 3 опциональных live-проверки пропущены; `npm run build` прошёл. Покрыты amych OAuth, отдельный admin-вход/бюджет, повторы, возвраты и тестовая маршрутизация. Это **не** полноценный многоканальный production end-to-end тест. Старые shell PostgreSQL-конкурентные сценарии не запускались в production. Два реальных эфира и выдача реального предмета в основной инвентарь в рамках аудита не проверялись.

## Порядок интеграции

1. Добавить заявки/решения/отзыв и общий серверный доступ на основном сайте; существующие тестовые записи не одобрять автоматически.
2. Перенести отдельный бюджет и промокоды в атомарные RPC с полной стоимостью обязательств; реализовать provenance выигранных предметов.
3. Привести primary и secondary round paths к единому streamer scope, атомарному старту/стопу/финализации; заменить небезопасную активацию промокодов.
4. Подключить подтверждённые подписки Twitch, транзакционный ingestion и отдельные OBS; провести всю матрицу на изолированном PostgreSQL.
5. Выпустить с заблокированным доступом до одобрения, затем владелец сайта одобряет amych, пополняет его отдельный бюджет; amych сам даёт Twitch-согласие. После контрольной выдачи на основном сайте подключаются следующие стримеры.
